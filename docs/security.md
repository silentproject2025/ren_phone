# Security and privacy

This project is intended as a personal, experimental device. Consider the following before using it with sensitive data or networks.

| Area | Current state | Recommendation |
|---|---|---|
| TLS certificates | Not verified (`setInsecure()`) in network features, including Chat. | Do not send sensitive information. |
| SIP calls | SIP signalling runs over plain TCP/UDP (no TLS yet); RTP audio is not encrypted; the password is sent as a *hash digest*. | Use an account dedicated to this device; assume calls can be intercepted. |
| Gutenberg downloads | EPUB/TXT files are downloaded over HTTPS without certificate verification (`setInsecure()`) from `gutenberg.org` and `gutendex.com`. Integrity is checked (a CRC32 of the data on the SD card is compared with the data that arrived from the network, plus the ZIP structure), but the authenticity of the server is not. | Only download from the built-in sources; never open `.bad` files. |
| Web File Manager | Requires login (HTTP Basic, default user `admin`, random 8-character password generated on first start). The password is stored only as a salted PBKDF2-HMAC-SHA256 hash in NVS (never as plain text; the old plain-text format is migrated automatically). The File Explorer screen shows it masked (`********`) and only while this boot knows it (generated or changed since the last reboot): tap the password part to reveal it for 10 s, tap `[ubah]` to set your own (8-32 characters) or generate a new random one. After a reboot only the hash remains and the line shows `(tersimpan)`. The user name and password can also be changed from the web page itself (`/passwd`; the current password is required). Cross-site requests that change data are refused. The web interface answers only while the File Explorer screen is open and for 10 minutes after leaving it or after the last request (403 otherwise); Remote Control and the gamepad page are not affected. After 5 wrong passwords the login is locked, escalating 60 s, 5 min, 15 min, 1 h; the level is stored and survives a reboot, and a successful login resets it. Basic Auth over plain HTTP is not encrypted. | Use it only on networks you trust; the password can be read by anyone sniffing the same network. | <!-- WEBAUTH_V1 WEBAUTH_V2 -->
| API keys | `gemini_key.txt`, `nasa_key.txt` (and the NVS fallback used without an SD card) hold the key encrypted as `enc1:<hex>` (AES-256-CTR + HMAC-SHA256). The encryption key is derived from a random per-device secret in NVS plus the chip MAC, so a stolen or copied SD card cannot be read on another device (an SD card moved to another device simply shows an empty key). A plain-text key you paste into the file is accepted and encrypted automatically the next time it loads. This does **not** protect against someone who dumps the flash of this very device (NVS is not encrypted), and the key still travels in the request URL to Google/NASA. | Use keys with limited quotas; enable ESP32 flash encryption if you need protection against physical flash access. | <!-- KEYENC_V1 -->
| Remote Control | The AP uses WPA2 with a random password generated on first use (the old public default `accretion` is replaced automatically); access via home WiFi is refused by default; one viewer at a time. | Leave *Allow via home WiFi* off unless needed. | <!-- RCPASS_V1 -->
| TURN credentials | Stored on the device or in `/turn.cfg`. | Use short-lived credentials (for example Cloudflare with a TTL). |
| Settings backup | `.nbk` files on the SD card are unencrypted unless encryption is on; WiFi passwords, the SIP account, the Chat account, API keys and the Remote AP password are only included when the *Include passwords and API keys* switch is on. | Leave that switch off, or enable password encryption if secrets must be included; keep the SD card physically safe. |
| Device registry and public username | On first WiFi connection the device sends an anonymous 16-hex id (a hash of the chip MAC, the real MAC is not sent), firmware version, build, branch and display type to Supabase, once. If you set a **public username** in Profile, it is shown on the public dashboard together with display type, firmware version and join/last-seen dates. The device id is never shown publicly. A device with a username also checks in once per boot; a device without one stays silent after the first registration. | Leave the username empty to stay off the public list. Do not share the device id: it is what authorises a username change. Clear the username in Profile to leave the dashboard. |
| Online chess | The broker uses TLS without certificate verification, like Chat; the broker account is stored in NVS and `/chess.cfg` as plain text. | Use a dedicated broker account and do not reuse other passwords. |
| Broker logins from Supabase | The Chat and Chess logins are returned by the Supabase function `get_broker_config`. The publishable key in the public firmware can call it, so anyone who reads the repository can get the logins. The table itself is locked (RLS, no policy) and `anon` cannot read it directly; the request carries only the anonymous device id. | Treat the logins as not secret: use broker users made only for this project, with an ACL limited to `renphone/chat/#` and the chess topics, never an admin account. `enabled = false` in `broker_config` switches the feature off; an empty `RP_REG_URL` disables it in the firmware. |

| OTA updates | `Check update` reads `info.txt` from the release channel and checks size, MD5 and (new) the SHA-256 of the firmware while it is downloaded. **Optional, off by default:** put an ECDSA P-256 public key in `firmware/phone/ota_pubkey.h` and the phone only accepts updates whose `info.txt` carries a valid signature (`sig=`, over everything before that line). With a key set it also refuses the legacy release path (no `info.txt`) and installing from a manually typed URL. Local `.bin` updates from the SD card are not signed (physical access). Downloads still use `setInsecure()` for TLS (deferred), so the signature is what protects you from a tampered release. | Run `tools/ota_keygen.sh`, store `ota_private.pem` as the GitHub secret `OTA_SIGNING_KEY` (never commit it), build and flash that firmware once by cable/SD, then use OTA. | <!-- OTA_SIG_V1 -->

## Known gaps (deferred)

- **TLS certificate verification** (`setInsecure()`, ~25 places: Chat, chess broker, Gutenberg, OTA, ...) is still off. Planned: CA bundle or certificate pinning, starting with the places that carry credentials.
- `/chess.cfg` and `/turn.cfg` still keep their account/credentials as plain text on the SD card.
- Basic Auth is sent over plain HTTP; the Web File Manager is meant for trusted networks only.

## Reporting a vulnerability

If GitHub private vulnerability reporting is enabled for the repository (Security tab), use it; otherwise contact the maintainer directly instead of opening a public issue. Include the affected feature, steps to reproduce and the firmware version or branch.
